# ADR028-004-classify-stateful-service-placement

> **Naming**: file lives at `<repo>/specs/ADR028-004-classify-stateful-service-placement/proposal.md`. `ADR028-004-classify-stateful-service-placement` is `AREA-NNN-slug` (e.g. `TOOL-001-secret-drift`).

## Why

<!-- from issue #988: ADR028-004: Classify stateful platform services by state promotion and availability -->

Nine stateful PVCs run in both staging and prod for no decided reason: they sit in `infra/k8s/base/`, and both overlays inherit base, so a topology decision was made as a side effect of a packaging choice and no ADR records it. Three of them — `gitea`, `n8n`, `minio` — were operator-reported as empty and unused (the operator tests directly in prod, and staging `minio` has no consumer at all since `overlays/prod/backup.yaml` is prod-only); R5's verification (`verification.md`) confirmed it for gitea and minio but found staging n8n hosts one active workflow (`notify-router`, the notification fabric, NOTIFY-001) — reconstructable from git+SOPS via `toolkit infra n8n import`, so "verified empty" was overclaimed for n8n specifically. That finding, plus n8n's prod instance needing to be always-on (it is the live alerting path, not a personal tool like Gitea), changed n8n's own classification: unlike gitea and minio, **n8n stays dual, in place** — see R5 and the dedicated write-up in `verification.md`. Real data is about to land in Gitea and MinIO, which makes this the last moment their placement is a free decision rather than a stateful migration with a downtime window and metadata that git clones do not replicate.

## What

- A two-axis classification, recorded as an ADR amending [ADR-028](../../docs/adr/adr-028-operational-topology.md) and [ADR-037](../../docs/adr/adr-037-environment-promotion-strategy.md), applied to all nine stateful services: axis 1 asks whether the state has a promotion path in git (dual vs singleton), axis 2 applies ADR-028's 3 AM test (always-on vs on-demand). The axes are independent — "prod" is an environment, not a location.
- The staging twins of `gitea` and `minio` no longer exist: they leave `base/` and the platform tier becomes singleton. Its intended test path is an ephemeral restore from a prod backup rather than a permanently-live second instance — **declared as doctrine here, not operational**: #487 (verified restore) is open, so that path does not exist yet. It must NOT appear in this spec's acceptance criteria or the spec can never archive. **`n8n` is the exception**, decided during R5: its staging twin stays, because unlike gitea/minio its state is entirely git-projected (see R5).
- The ADR's table emits a value on **both** axes for **every** service, not only for Gitea. Gitea and MinIO's locations follow R1/R2 (Gitea confirmed to Beelink; MinIO's own move is out of scope). n8n's row is `dual` / `always-on, unchanged` — it never left K3s prod, so it needed no location decision.
- A CI gate fails when a stateful service in `base/` carries no classification, or when state with no git promotion path is duplicated across overlays — turning the rule from prose into something enforced.

## Out of scope

This spec spans more than one PR (the Discipline Gate names a multi-PR sequence as its own trigger), but a single PR still carries a single concern under the ~300-line cap. The list below is out of the **spec**, not merely out of its first PR.

- **MinIO's migration.** MinIO is classified here; it is not moved. Its destination follows from R3 and from the backup path chosen in the wider backup/DR work — moving it before that is deciding the offsite tier by accident.
- **A general promotion path for n8n workflows.** `notify-router`, the one workflow that exists today, is git-projected via `toolkit infra n8n import` (TOOL-009) — that is *why* n8n can stay dual (R5). But that mechanism is special-cased to this one workflow, not a general import/export route: a workflow authored by hand in either instance's UI would still drift with no way back, and n8n stays dual only on the condition that git+import remains the sole write path. The general gap is **already tracked, twice under one id**: [#501](https://github.com/mlorentedev/kubelab/issues/501) and [#688](https://github.com/mlorentedev/kubelab/issues/688) are both open as `APP-CONFIG-003` (a collision the 2026-07-02 platform audit already named), with [#691](https://github.com/mlorentedev/kubelab/issues/691) closed as `TOOL-009` on the import half for this one workflow. Reconciling those three belongs to the backlog triage ([#823](https://github.com/mlorentedev/kubelab/issues/823)), not here — filing a fourth ticket for the same concern is the pathology, not the fix.
- **[#264](https://github.com/mlorentedev/kubelab/issues/264) (official Helm charts) and [#503](https://github.com/mlorentedev/kubelab/issues/503) (Gitea mirror, org/team, webhooks).** Both touch the same three services and both already have tickets with their own gates. Absorbing ticketed work here would orphan or duplicate those gates — the ID-collision pathology the 2026-07-02 platform audit documented (ANSIBLE-026 across two issues, TOOL-009 across three places). Packaging is also orthogonal to placement: doing both at once means a break cannot be attributed.
- **Restructuring `base/` into a `platform/` tier.** Removing three services invites reorganising the rest along the management/workload split the reference audit found. That is a layout refactor and it depends on this classification being settled first.
- **[#479](https://github.com/mlorentedev/kubelab/issues/479) and [#487](https://github.com/mlorentedev/kubelab/issues/487) (offsite age key, verified restore).** They gate *using* these services with real data. They do not gate *deciding* their placement, and this spec closes without them.

## Risks / open questions

**All six below are MUST-RESOLVE.** R1 through R6 are all resolved as of 2026-08-12 (evidence in `verification.md`) — `tasks.md` can unfreeze.

- **R1 — RESOLVED (measured, `verification.md`).** Which node Gitea lands on. Its role is settled (private repos and private experiments only; Argo CD keeps reconciling from GitHub), so it no longer inherits prod's always-on requirement and the operator only pushes with the homelab powered on. Beelink — ADR-028's own "Platform Node" — was measured live: 7.18 GB RAM free of 8.09 GB, 57.2 GB disk free, idle load. Summed against the *declared* limits of everything already there (glances + minio + github-runner, worst case 6.75 GB) plus Gitea's own K8s-declared limit (256Mi), the worst case still leaves ~1.1 GB headroom — and that worst case is mitigated by ADR-030 making self-hosted CI idle-by-default. Not a blocker.
- **R2 — RESOLVED (decided, `verification.md`).** Beelink is Docker Compose, not K3s, so Gitea leaves Kustomize and Argo CD's reconciliation. Decided deliberately, not a regression: this is the same shape already in the repo twice — Headscale outside K3s (ADR-015) and the Argo CD hub outside both clusters — for the same reason, a platform component can't be reconciled by the GitOps system that depends on reaching it. Gitea hosting the repos Argo CD would otherwise fetch from is exactly that trap; the proposal already avoids it by keeping Argo CD on GitHub.
- **R3 — RESOLVED, and inverted from the original framing (`verification.md`).** The original text said the prod backup CronJob loses its *destination* if MinIO moves. MinIO's migration is out of scope for this spec (see above), so `http://minio:9000` keeps resolving throughout — that framing was wrong. What actually breaks, inside this spec's own scope, is the *source*: `overlays/prod/backup.yaml` mounts the `gitea-data` PVC that R1's move task deletes. Kustomize renders a CronJob with a dangling PVC claim without error, `kubectl apply` accepts it, and `backup.yaml` is prod-only so staging e2e never exercises it — AC3's render-and-e2e safety net has a hole here. **The move task for Gitea must edit `backup.yaml` in the same change**, dropping its PVC mount and backup step, keeping `authelia-data` and — since R5 settled n8n as dual, unmoved — `n8n-data` too. This is now a named MUST for R6's sweep, not an implicit item on its consumer list. Separately, and not something this spec resolves: the in-cluster MinIO destination was never a real offsite copy (same-cluster storage doesn't survive a cluster/node loss) — ADR-049 D3 already routes the real offsite tiers to Hetzner Storage Box (Borg) and R2 (restic, tracked as BACKUP-043 #596, open, neither pipeline built yet). This spec's job is only to stop the CronJob from silently mounting a deleted claim, not to build that pipeline.
- **R4 — RESOLVED, with one structural wrinkle now known (`verification.md`).** Nothing prevents the classification from being fields under `common.yaml`, read by a static test in the style of `tests/test_spoke_rbac_covers_manifests.py` — confirmed by resolving all eight stateful services (nine PVCs, `crowdsec` owns two) to an existing config block. Seven live under `apps.services.<category>.<name>`, a free-form dict already carrying many attributes. **The eighth, `postgres`, lives at `infra.postgres.*` instead — deliberately, per ADR-051, the same "shared multi-consumer service" pattern ADR-036 established for SMTP.** The static test's design must therefore resolve each service's block from wherever it actually lives, not assume a single tree — a concrete blueprint (enumerate PVCs from manifests, resolve classification per-service, fail listing what's missing, with a demonstrated-red negative control) is in `verification.md`, ready for the implementation task.

  The gate's acceptance criterion must assert the **negative** control, not just the positive: "the test FAILS when a stateful service is left unclassified". Two vacuous controls shipped on a single day during OBS-007 — a negative control that broke unreferenced code, and a guard whose bad import was swallowed by a broad `except`, silently skipping 13 tests while reporting green. A gate that cannot be shown to fail is not a gate.

- **R6 — RESOLVED, verified rather than re-asserted, then narrowed once R5 kept n8n dual (`verification.md`).** `overlays/prod/patches.yaml` patches **seven** targets that live in `base/`, confirmed exact: `gitea-config`, `gitea`, `n8n-config`, `n8n`, `minio-config`, `minio-api`, `minio-console`. **Only gitea's and minio's five move** — `n8n-config` and `n8n` stay in `base/` untouched, since n8n isn't retiring. Kustomize fails when a patch has no target, so removing the moving ones from base without relocating them into the prod overlay in the same change breaks the prod render immediately. **This fixes the task order; it is not optional sequencing.**

  Cross-cutting consumers, checked against the repo rather than assumed, then re-scoped to gitea+minio only: `tests/e2e/expectations.py` (gitea/minio entries only — n8n's stays as-is) and `SECRET_CATALOG` (gitea/minio entries, confirmed; n8n was never in this list). Two corrections from that check: "Homepage `services.yaml`" was the wrong pointer — the committed file is a static scaffold; the real consumer is `toolkit/scripts/sync_homepage_config.py`, which hardcodes tiles per service — only the gitea and minio ones are removed, n8n's stays. And "Authelia's staging access rules and OIDC clients" was two mechanisms conflated as one — access rules are auto-derived from `enable_auth`/`auth_level` and need no edit; only the hardcoded OIDC client list (`apps.services.security.authelia.oidc_clients`) does, and only its `gitea-oidc`/`minio-oidc` entries (n8n has none — built-in auth). Plus R3's own addition, `overlays/prod/backup.yaml` — now only its `gitea-data` mount, not `n8n-data`. Same 7 files touched as originally found; each one's diff is smaller now that n8n's entries are excluded throughout. Full precise edit set in `verification.md`.

  The outcome check stays the safety net regardless of the list's precision now: both overlays must render and `make test-e2e ENV=staging` must be green after the retirement, since a future service could still add a consumer this sweep didn't know about.
- **R5 — RESOLVED, and it caught what it was designed to catch, which changed n8n's classification entirely (`verification.md`).** "Empty" had to be proven per instance before any PVC is deleted, not assumed — the operator-reported "gitea, n8n and minio unused" was wrong for one of the three. Gitea and MinIO are confirmed empty (authenticated repo search, empty `/data`) and retire as planned. n8n hosts one active workflow (`notify-router`, the notification fabric) and its credential, git-projected via `toolkit infra n8n import` (TOOL-009) — and its prod instance is the live alerting path, which by ADR-028's own 3 AM test has to stay always-on, unlike Gitea. Both facts together mean n8n doesn't fit the retire-to-singleton treatment the other two get: **n8n stays dual, in place, on the condition that git+import remains its only write path** (a UI-authored workflow would fork it instantly — the general-case gap tracked by #501/#688 is exactly why this condition matters). Full industry-practice write-up, with sources, in `verification.md`. The Why and What sections are corrected accordingly.

## Acceptance criteria

Observable outcomes. Each must be testable.

Deliberately absent: anything asserting the ephemeral restore-from-prod-backup test path. That is declared doctrine, not present capability (#487 is open), and an acceptance criterion depending on it would make this spec unarchivable.

- [ ] **AC1** — The ADR is merged and emits a value on **both** axes for all **eight** stateful services (nine PVCs — `crowdsec` owns two), with a location cell filled per singleton (not only for Gitea). A recorded deferral naming its ticket counts as filled; a blank cell does not. *(Corrected 2026-08-12, while still `draft`: the original said "nine stateful services", conflating the PVC count with the service count and making the criterion untestable as written — R4 had already established eight services / nine PVCs.)*
- [ ] **AC2** — The classification is readable from a single SSOT, and a static test fails when a stateful service in `infra/k8s/base/` carries no classification. Verified by **demonstrating the failure**: remove one service's classification, show the test red, restore it, show it green. A passing test alone does not satisfy this criterion.
- [ ] **AC3** — After the retirement, `kubectl kustomize` renders **both** overlays without error and `make test-e2e ENV=staging` is green. This is the criterion that forces the consumer sweep in R6 rather than an enumeration that can miss a file.
- [ ] **AC4** — Per-instance emptiness evidence for staging `gitea` and `minio` (n8n stays dual per R5 — nothing is deleted there, so it drops out of this criterion; its evidence stays in `verification.md` as the record of why the classification flipped), **and for any prod instance being moved (e.g. prod `gitea-data`, per R1)** — repo count, bucket listing — is captured as command output in `verification.md` **before** any PVC deletion task runs. Found while resolving R3: R1's move deletes the prod PVC too, and the original AC4 only required proof for staging.
